# CamGuard

Grabación por movimiento de cámaras iCSee a batería (una o varias), de dispositivos Tuya con cámara (cámaras, timbres, cerraduras como la XOOMI C20) y de cámaras ONVIF enchufadas (Imou Cue 2). go2rtc mantiene la única conexión con cada cámara (DVRIP :34567) y la reparte por RTSP (grabación) y WebRTC (vivo). Los streams de go2rtc no están en `go2rtc.yaml`: los registra la API (slice `Streams`) a partir de las cámaras en BD. Diseño completo en `.claude/plans/Sprint1_Visualizacion/plan.md` (planes por sprint en `.claude/plans/`); resultados de campo en `poc/README.md`.

## Estructura

- `backend/` — .NET 10, un solo proyecto `CamGuard.Api` organizado en **vertical slices**. Pruebas en `tests/CamGuard.Tests` con **TUnit**.
- `frontend/` — React + Vite + TypeScript, TanStack Query, React Router, SignalR. nginx lo sirve y hace proxy de `/api` y `/hubs`.
- `keycloak/` — imagen de Keycloak: `realm-camguard.json` (realm, cliente `camguard-web`, primer usuario; se importa solo si el realm no existe) y `theme/` (Keycloakify: login en `src/login` sin CSS de Keycloak: `Template.tsx` propio, clases `cg-*` mapeadas en `KcPage.tsx` y estilos en `main.css`, correos FreeMarker en `src/email`). nginx lo publica en `/auth`.
- `docker-compose.yml`, `go2rtc.yaml`, `.env.example` — despliegue. `poc/` — scripts de la fase 1. `scripts/backup-db.sh` — respaldo de Postgres (CamGuard y Keycloak); `scripts/verify-backup.sh` lo restaura en un Postgres temporal y escribe `backups/last-verify.json`. `scripts/backup-local.ps1` (comando `/formatear`) — respaldo de lo que git no guarda antes de formatear. `backend/tools/CamGuard.DbMigrator` — copia única de una base SQL Server antigua a Postgres.

## Comandos

```sh
cd backend && dotnet build                 # SDK fijado en global.json (10.0.x)
cd backend && dotnet test                  # TUnit sobre Microsoft.Testing.Platform (global.json "test.runner")
cd backend && dotnet ef migrations add <Nombre> --project src/CamGuard.Api --output-dir Common/Data/Migrations
cd frontend && npm run build && npm run lint   # tsc + vite, oxlint
cd keycloak/theme && npm run build             # tema; el .jar lo genera keycloak/Dockerfile (Maven)
docker compose up -d --build
```

La prueba del modelo real (`[Category("Model")]`) usa `backend/models/yolox_nano.onnx` y `backend/models/samples/person.jpg` (o `CAMGUARD_DETECTION_MODEL`/`CAMGUARD_DETECTION_SAMPLE`), ignorados por git; si faltan, se omite. En Development la API busca el modelo en `backend/models/`.

`dotnet ef` es una herramienta local (`backend/dotnet-tools.json`): usa `dotnet tool restore` si falta. Las migraciones se aplican solas al arrancar (`DatabaseInitializer`), con reintentos mientras Postgres levanta (servicio `db`, propio de CamGuard; Keycloak usa `keycloak-db`).

## Backend: vertical slices

- `Features/<Slice>/` contiene todo lo de una capacidad: endpoint, request/response, validación, lógica y su `BackgroundService`. No hay capas Core/Infrastructure ni MediatR.
- Endpoints: clase anidada `Endpoint : IEndpoint` dentro de una clase estática por caso de uso (`ListRecordings`, `UpdateSettings`…). Se descubren por reflexión (`AddEndpoints`/`MapEndpoints`) bajo el grupo `/api`. Un archivo nuevo con `IEndpoint` queda registrado solo.
- Cada slice con servicios expone `Add<Slice>Feature(...)`, que se llama en `Program.cs`.
- `Common/` solo para lo compartido de verdad: `AppDbContext` y entidades, `IVideoStorage` (S3/R2), `INotifier` (ntfy, ver Notifications), `RetryPolicy`, `EventsHub` (SignalR), validación de tokens de Keycloak (`AuthSetup`), opciones y `CameraEventChannel`.
- Entre slices: Monitoring → Capture por `CameraEventChannel` y Monitoring → Devices por `CameraAwakeChannel` (aviso de "despertó"); Capture → Detection por `DetectionQueue` y Detection → Upload por `UploadQueue` (rutas locales del clip en `ClipPaths`); Cameras y Live leen `CameraStateStore` (Monitoring); Cameras → Streams por `StreamSyncTrigger`; Tuya y Onvif publican despierta/dormida con `CameraStatePublisher` (Monitoring); Onvif → Streams por `StreamSyncTrigger` (perfiles de video descubiertos); Capture y Live llaman a `TuyaStreamPreparer` antes de abrir el stream de un dispositivo Tuya; Health lee `UploadHealth` (Upload), `TuyaConnectionState` (Tuya), `OnvifConnectionState` (Onvif; también Cameras) y `NotifierHealth`/`NotificationOutbox` (Common); Upload usa `PriorityEvents` (Detection).
- Devices: `DvripClient` (protocolo Sofia, puerto 34567) lee modelo, batería y SD y aplica la sensibilidad pendiente **solo cuando la cámara ya despertó** (`DeviceInfoService`, nunca la despierta). Las claves DVRIP de batería y detección dependen del firmware: se prueban en orden (`DvripQueries`) y lo que no exista queda `null`. En Development, `GET /api/cameras/{id}/dvrip-probe` devuelve las respuestas crudas para descubrirlas. "Probar conexión" es `POST /api/cameras/test`.
- Streams: `StreamSyncService` registra con `PATCH /api/streams` (no `PUT`: ese intenta escribir `go2rtc.yaml`, montado `:ro`) un stream por iCSee habilitada cada `Streams:SyncSeconds` y al pedirlo `StreamSyncTrigger`; quita los que no son de ninguna cámara. Los de dispositivos Tuya no los toca (`managedElsewhere`). La decisión es `StreamSyncPlan.Compute` (pura).
- Tuya (`Features/Tuya/`): cualquier dispositivo Tuya con cámara, `Camera.Kind = Tuya` (sin IP ni DVRIP; `TuyaDeviceId`), todo por la Tuya Cloud API con las credenciales del proyecto (`Tuya:*`; vacías = desactivado). `TuyaApiClient` firma con `TuyaSigner` (igual que `poc/tuya/tuya-api.ps1`). `TuyaEventService` escucha el Message Service (Pulsar por WebSocket; `TuyaMessageDecoder` descifra AES ECB/GCM) y traduce DPs con `TuyaEventRules`: movimiento (`movement_detect_pic`), timbre y alarmas graban (`TuyaActivationWindow`: no hay aviso de "dormida", la activación dura `Tuya:ActivationSeconds`) y las aperturas solo se registran; todo se avisa al instante por ntfy y queda en `CameraEvent` (`Detail`). Una cámara sin detección propia (la cerradura) puede despertarse con sensores Tuya: `Camera.TuyaTriggerDeviceIds` (p. ej. un PIR, DP `pir`); su movimiento graba sin aviso inmediato. La cerradura avisa sus eventos con foto por el DP `initiative_message` (`cmd = door_lock_video`, `ext.type` 18 = timbre). La batería sale de `residual_electricity`/`wireless_electricity`. Un firmware con otros códigos se descubre con `poc/tuya/probe-device.ps1` y se agrega en `TuyaEventRules`. La URL de video (RTSPS) caduca: `TuyaStreamPreparer` pide una nueva y la registra en go2rtc justo antes de grabar o ver en vivo (eso despierta el dispositivo; el primer cuadro tarda ~30–40 s, de ahí `Tuya:StartupGraceSeconds`). No registres esa URL en logs.
- Onvif (`Features/Onvif/`): cámara enchufada y siempre encendida, `Camera.Kind = Onvif`, con `Ip`, `OnvifPort`, `Username` y la contraseña cifrada como las iCSee.
  - `OnvifClient` es SOAP sobre `HttpClient`, sin WCF: `OnvifSoap` arma el sobre (WS-Security `PasswordDigest` con el desfase de reloj de la cámara) y `OnvifParser` lee por nombre local.
  - `OnvifEventService` mantiene una suscripción PullPoint por cámara (`Renew` a mitad de vigencia, reconexión con `RetryPolicy`). `OnvifEventRules` traduce tópicos (`VideoSource/MotionAlarm` `State`, `CellMotionDetector` `IsMotion`, `TamperDetector`).
  - `OnvifMotionTracker` (pura) convierte el movimiento en despierta/dormida, con `Onvif:AsleepDelaySeconds` de gracia. La manipulación queda como `CameraEvent` `Tamper` y se avisa por ntfy.
  - Al conectar descubre los perfiles: el de mayor resolución graba y el de menor es el vivo. Los guarda en `OnvifMainStreamUri`/`OnvifSubStreamUri` sin credenciales y el códec real en `OnvifMainCodec`, leído del SDP con `RtspDescribe`, porque ONVIF Media 1 no distingue H.265.
  - `StreamSyncService` registra `{stream}` (principal) y `{stream}_sub` (vivo, `Go2rtcStreamNames.Live`). Con H.265, FFmpeg agrega `-tag:v hvc1`.
  - El vivo no exige "despierta". Health abre `offline:{id}` en lugar de `silent:{id}`.
  - Tópicos de otro fabricante: revísalos con `poc/imou/onvif-events.ps1` y agrégalos en `OnvifEventRules`.
- Detection (`Features/Detection/`): IA local que decide qué clips se suben, **después** de grabar y de a un clip por vez (en la Raspberry Pi nunca compite con FFmpeg grabando). `FrameSampler` saca con FFmpeg 1 cuadro/s (tope `Detection:MaxFrames`) en BGR crudo de 416×416 por stdout; `OnnxObjectDetector` corre YOLOX-nano (ONNX Runtime, Apache-2.0; el `Dockerfile` lo descarga con hash fijo a `/app/models/`); `YoloxDecoder` toma la mejor confianza (obj × cls) por clase, sin cajas ni NMS; `DetectionPolicy` (pura) etiqueta (`persona` gana a los animales, `nada` si no hay) y decide según `Camera.DetectionMode`: `Off` no analiza, `Tag` (por defecto) etiqueta y sube todo, `Filter` descarta (`Discarded`, borra los archivos, nunca llega a R2) lo que no tenga personas ni animales. Corta en el primer cuadro positivo. **Fail-open**: modelo ausente, FFmpeg con error o excepción de ONNX → se sube con `Detection = null` y un warning. Un clip con timbre/alarma Tuya (`Doorbell`, `Alarm`, `LockEvent`) cerca de la grabación nunca se descarta. El estado persistente es `Status = Analyzing` (se reencola al arrancar). En `Filter`, el movimiento Tuya no se avisa al instante: solo el clip confirmado. `DetectionMinConfidence` se edita en Ajustes.
- Upload (`UploadService`): tras un fallo corta el lote y pausa toda la cola (`RetryPolicy` sobre el máximo entre los intentos del clip y los fallos seguidos); el primer éxito la limpia. Sin internet los `Uploading` se acumulan en `{DataDirectory}/clips`: a lo más una vez por minuto, en el mismo ciclo (único hilo que toca la cola), si pasan `AppSettings.LocalMaxGb` o queda menos de `Upload:MinFreeDiskMb` libre se borran por `LocalEvictionPolicy` (pura): `nada` → sin analizar → animal → persona → timbre/alarma/`LockEvent` (`PriorityEvents`, en Detection), y dentro de cada uno los más antiguos. Quedan `Evicted` (sin `StorageKey`, como `Discarded`). Solo los `Uploading`: los `Recording` están abiertos por FFmpeg.
- Notifications (`Common/Notifications`): el `INotifier` de la app es `OutboxNotifier`; envía al instante si la bandeja está vacía y si no (o si falla) guarda el aviso en `{DataDirectory}/notify-queue` (JSON por aviso, tope 500) y vuelve **sin lanzar**. `NotificationOutboxService` los envía en orden con backoff; `DelayedNotification.Prepare` descarta los de más de `Ntfy:MaxDelayHours` y antepone "Retrasado (hh:mm) · " a los de más de 2 min. `NtfyNotifier` (timeout 10 s) solo se usa por dentro. `NotifierHealth` se muestra en Estado como servicio `ntfy`, sin abrir problema.
- Retention (`RetentionService`, una vez al día): borra los clips con `StartedAt` anterior a `RetentionDays` (BD y R2) y luego barre el bucket borrando todo objeto vencido por `LastModified`, tenga o no fila (huérfanos); solo toca claves con la forma de `StorageKeys` (`IsManaged`).
- Health (`Features/Health/`): `HealthMonitorService` revisa cada `Health:CheckMinutes` solo lo que ya se sabe (nunca despierta una cámara): batería (`Camera.BatteryPercent`, que escriben Devices y Tuya; cada lectura nueva va a `BatteryReading`, 90 días), último `Awake`, go2rtc (`GET api`), Tuya, R2, la cola (`Recording` en `Uploading`), el disco de `DataDirectory` y los respaldos (`Health:BackupDirectory`, montado desde `./backups`; vacío = no se revisan): `backup` si el último `camguard-*.sql.gz` tiene más de `BackupMaxAgeHours`, `backup-verify` si `last-verify.json` dice `ok: false` o tiene más de `BackupVerifyMaxAgeDays`. La lógica pura es `BatteryForecast` (regresión desde la última carga), `HealthEvaluator` (problemas con clave estable, histéresis de batería, gracia de servicios) y `HealthAlertPolicy` (abrir, repetir cada `RepeatHours`, resolver). Los problemas abiertos quedan en `HealthAlert`, así un reinicio no repite avisos. Se avisa por ntfy ("Problema: …" / "Resuelto: …") si `AppSettings.HealthAlertsEnabled`. `GET /api/status` devuelve el último snapshot (204 antes de la primera revisión) y `HealthUpdated` (SignalR) avisa cuando cambian los problemas; no confundir con `/health`, el health check anónimo.
- `Camera.Rotation` (0/90/180/270) gira el video: en los clips como metadato (`-display_rotation`, sin recodificar) y en vivo por CSS (`.frame[data-rotation]`).
- La contraseña DVRIP de cada cámara va cifrada en BD (`CameraSecretProtector`, Data Protection con llaves en `{DataDirectory}/keys`) y nunca sale en una respuesta (`HasPassword`). No registres el origen `dvrip://` en logs: lleva la contraseña.
- La lógica pura queda en métodos `static` o en clases sin dependencias (`CameraStateTracker`, `ActivationGate`, `RetryPolicy`, `RetentionPolicy`, `Validate(...)`, `FfmpegRecorder.RecordArguments`) para probarla sin infraestructura. Mantén ese patrón al agregar reglas.
- Todo endpoint exige un access token de Keycloak (fallback policy; issuer `Auth:Authority`, audience `camguard-api`). Lo público lleva `.AllowAnonymous()` explícito. No hay login propio ni usuarios en la BD: los usuarios viven en Keycloak.
- Usa `TimeProvider` (inyectado) en lugar de `DateTime.Now`. La lógica pura recibe `now` por parámetro.

## Flujo de una activación

`CameraMonitorService` sondea TCP cada 1 s (despierta con 1 éxito, dormida tras `AsleepAfterFailures` fallos) → `RecordingService` respeta `ActivationGate` (una grabación por cámara + enfriamiento) y lanza FFmpeg contra `rtsp://go2rtc:8554/<stream>` con tope `MaxClipSeconds`; al dormirse o al apagar el host le escribe `q` por stdin para cerrar el MP4 limpiamente → `Analyzing` y `DetectionQueue` → `DetectionService` etiqueta (o descarta, en `Filter`) → `Uploading` y `UploadQueue` (JSON en `{DataDirectory}/queue`) → `UploadService` sube a R2 con backoff infinito, marca `Uploaded`, emite `RecordingCompleted` y notifica por ntfy ("Persona: …", "Animal (perro): …" o "Movimiento: …"). El archivo local se borra solo tras confirmar la subida.

Cámara ONVIF: `MotionAlarm` `State=true` en PullMessages → `OnvifEventService` publica "despertó" → `RecordingService` graba `{stream}` (principal) → con `State=false` más `AsleepDelaySeconds`, "dormida".

Dispositivo Tuya: mensaje de movimiento/timbre/alarma (`movement_detect_pic`, `doorbell`, `alarm_lock`…) → `TuyaEventService` avisa por ntfy y publica "despertó" → `RecordingService` llama a `TuyaStreamPreparer` y graba igual que una iCSee → "dormida" al vencer la ventana de activación.

## Detalles que ya causaron bugs

- Postgres (`timestamptz`) solo acepta `DateTimeOffset` en UTC: lo guardado sale de `TimeProvider.GetUtcNow()`, y las fechas que manda el navegador (`from`/`to`, `todayFrom`…) se pasan con `ToUniversalTime()` antes de consultar. Las comparaciones de texto distinguen mayúsculas.
- Formatos de fecha en claves o nombres de archivo: usa `CultureInfo.InvariantCulture`. En un formato, `/` es el separador de la cultura actual (en es-* puede ser `-`).
- AWS SDK v4 con R2: checksums en `WHEN_REQUIRED`; `DisablePayloadSigning` y el protocolo de las URLs prefirmadas dependen de que el endpoint sea https (el SDK firma con https por defecto).
- nginx debe resolver `api` en cada petición (`resolver 127.0.0.11` + variable en `proxy_pass`); si no, da 502 tras recrear el contenedor de la API.
- FFmpeg: el audio G.711 de las iCSee no cabe en MP4, por eso es `-c:v copy -c:a aac`. No mates el proceso: un MP4 sin cerrar no tiene `moov atom` y no se puede reproducir.
- Keycloak: `KC_HOSTNAME=${PUBLIC_URL}/auth` fija el issuer; la web debe abrirse con `PUBLIC_URL` y la API lee discovery/JWKS por `keycloak:8080` (`KC_HOSTNAME_BACKCHANNEL_DYNAMIC`). En el realm importado, `temporary: true` en la credencial no fuerza el cambio: hace falta `requiredActions: ["UPDATE_PASSWORD"]`. Un `SMTP_FROM` vacío hace fallar el import. El realm se importa una sola vez: cambiar `PUBLIC_URL` (p. ej. a https con Tailscale Serve, `docs/tailscale.md`) exige actualizar a mano las redirect URIs de `camguard-web`. Detrás de un proxy https, nginx reenvía su `X-Forwarded-Proto` (`map $forwarded_proto`); sin eso Keycloak cree que la conexión es http.
- FFmpeg `fps=1` descarta el único cuadro de un clip de menos de 1 s (o de una foto): el muestreo de la IA usa `fps=1:eof_action=pass`.
- go2rtc no usa trickle ICE: el `LivePlayer` espera a que termine la recolección de candidatos antes de enviar la oferta.
- go2rtc rechaza por API (`PATCH /api/streams`) los orígenes `expr:`, `exec:` y `echo:` ("source from insecure producer") y no hay opción para permitirlos: un origen dinámico se registra desde la API justo antes de usarlo (`TuyaStreamPreparer`).
- ONVIF: las direcciones que informa la cámara (XAddr, suscripción, URIs RTSP) pueden venir vacías, relativas, con `0.0.0.0` o con otra IP de la cámara (las Dahua también responden en `192.168.1.108`). Siempre se reapuntan a la IP configurada con `OnvifParser.RebaseHttp`/`RebaseRtsp`. `-tag:v hvc1` solo con H.265: en un H.264 hace fallar el muxer. Varios logins fallidos bloquean la cuenta de una Dahua: tras un `Unauthorized` el reintento espera más.
- Tuya Message Service: un 401 al abrir el WebSocket suele indicar que el servicio no está activado en el proyecto (pestaña *Message Service*).

## Frontend

- `src/main.tsx` llama a `oidcEarlyInit` antes de cargar nada y `bootstrap.tsx` espera a `initOidc()` (`src/auth/oidc.ts`, `autoLogin`: sin sesión redirige a Keycloak). `src/api/client.ts` pide el token a oidc-spa en cada petición (lo renueva solo); un 401 cierra la sesión.
- `src/api/types.ts` (espejo de los DTO de la API; enums como string).
- Estilo: `src/index.css` con los tokens del rediseño (`designs/CamGuard_Rediseño`), oscuro por defecto y claro con `html[data-theme=light]` (`useTheme`, guardado en localStorage). Fuentes Geist autoalojadas (`@fontsource-variable`). Sin librerías de UI: clases CSS planas.
- `EventsHubProvider` mantiene una sola conexión de SignalR y actualiza la caché de TanStack Query: `['cameras']` con `CameraAwake`/`CameraAsleep`; invalida `['recordings']` con `RecordingCompleted` y `['status']` (panel Estado y contador de la pestaña) con `HealthUpdated`.
- Features en `src/features/<área>/`. Se prefiere estado derivado en lugar de `setState` dentro de `useEffect` (lo marca oxlint).
- Las URLs prefirmadas caducan (`Storage:PresignedUrlMinutes`): no se cachean entre aperturas del reproductor.
- PWA: `public/manifest.webmanifest` (atajos `/live` y `/latest`), `public/sw.js` (solo la página `offline.html` en navegaciones fallidas; nunca guarda `/api`, `/hubs` ni `/auth`; para publicar un cambio, sube `CACHE`), registrado en `bootstrap.tsx` tras `initOidc()` y solo en producción. Instalar exige HTTPS (Tailscale Serve, ver README).
- Vivo (`LivePlayer`): con `autoConnect` (vista de una cámara) se conecta cuando la cámara despierta (una ONVIF, siempre: está enchufada); el mosaico `/live` usa `autoConnect={false}` y nunca conecta solo, ni una iCSee ya despierta. Con la página oculta (`usePageVisible`) siempre se desconecta, para no mantener despierta una cámara a batería.

## Planes (modo plan)

- Todo plan queda en `.claude/plans/Sprint<N>_<Nombre>/plan.md` (`<Nombre>` corto en PascalCase y en español, sin tildes), p. ej. `Sprint1_Visualizacion/plan.md`, `Sprint2_Multicamara/plan.md`.
- El sprint es el siguiente al mayor que exista en `.claude/plans/`, salvo que el usuario indique otro o el plan amplíe uno existente. Los sprints ya reservados tienen carpeta con `alcance.md` y sin `plan.md`: el próximo plan es el de menor número entre ellos (léelo antes de planificar).
- `plansDirectory` (`.claude/settings.json`) guarda el borrador en `.claude/plans/` con nombre aleatorio; al aprobarse, el hook `PostToolUse` de `ExitPlanMode` ejecuta `.claude/hooks/move-plan.ps1`, que lo mueve a `Sprint<N>_<Nombre>/plan.md` (número y nombre del primer sprint reservado; si no hay, el siguiente con el nombre tomado del primer `#` del plan). No lo muevas a mano; si quedó un plan suelto, corre el script.
- Revisión de seguridad por sprint: `/cerrar-sprint [N]` revisa el diff desde la última revisión (vulnerabilidades en el código, dependencias con `dotnet list package --vulnerable` y `npm audit`) y escribe `Sprint<N>_<Nombre>/seguridad.md` (frontmatter `commit:`, base de la siguiente). Un sprint termina cuando se aprueba otro plan: el hook de `ExitPlanMode` también corre `.claude/hooks/check-sprint-security.ps1`, que pide la revisión de los sprints con `plan.md` y sin `seguridad.md` (salvo el en curso, el `plan.md` más reciente, y los exentos de `security-baseline.json`) antes de implementar.

## Convenciones

- Código, nombres y comentarios: identificadores en inglés y textos visibles, logs y comentarios en español.
- Pruebas TUnit: `[Test]`, `[Arguments]`, `await Assert.That(...)`, nombres `Metodo_Escenario_Resultado`, carpetas espejo de `Features/`.
- Secretos solo en `.env` (ignorado por git) o variables de entorno; nunca en `appsettings.json`. `appsettings.Development.json` lleva solo valores de desarrollo.
